GIT main commands

git checkout - создание ветки (флаг -b позволяет переключиться на ветку сразу)

git switch имя_ветки - переключиться на ветку 

git merge имя ветки - слияние двух веток указанной и текущей. Текущая ветка считается той в которой ты находишься ее можно посмотреть через git brunch оно выводит список всех веток и помечает ветку в которой ты находишься. 
Коммиты с их индексом (хеш кодом) можно увидеть командой git status --oneline --graph
Существует 3 типа слияния: 
- Fast-forward просто сдвигает указатель целевая ветка не изменилась. (насколько понял я коммиты идут друг за другом и не различаются по веткам у нас идет одно индексирование коммитов на все ветки и когда мы объединяем ветки с коммитами которые идут друг за другом условно main A - B - C. featuer D - E делая mergue у нас будет ветка в main A - B - C - D и нам не потребуется новый коммит. Но это не срабоотает если у нас идут коммиты типа main A - B - C - F feature D - E. после мерджа веток нужно будет создавать отдельный коммит)
- Merge коммит - вторая версия коммита противоположность fast-forward та ситуация когда нужно для merge создавать новый коммит.
- Конфликт (пересекающися изменения) блокируется до ручного merge. Ситуация после merge коммита в мы объединяем ветку main в ней последний коммит F в котором написано улсовно "hello world" в коммите D написано "hello python" конфликт родителя какую версию выбрать. если я понял в родителе было "hello" или ничего не было. Что бы увидеть в каком файле возникает конфликт git status покажет нам это. git status                    # Какие файлы в конфликте
git diff                      # Подробно конфликты
git log --merge --oneline     # Конфликтующие коммиты
git merge --abort             # ОТМЕНИТЬ merge
git show :1:file.txt          # Версия из общей ветки
git show :2:file.txt          # Версия из main
git show :3:file.txt          # Версия из feature

- git rebase (у коммитов как я понял стоит последовательное наследование и merge commit для merge считается грязным сливанием и нужно всегда стремиться к fast forward и что бы избежать merge сливания нужно сделать перенаследование индексов это и позволяет сделать путем rebase) 

-git fetch - этап который следует делать перед git pull синхронизировать файлы с файлами репозитория без изменений в коде. 

-git revert - отменяет указанный коммит но не удаляет его из истории коммитов. Можно отменять диапазон коммитов.
История ДО:
A ← B ← C ← D(ошибка) ← E

git revert D
История ПОСЛЕ:
A ← B ← C ← D(ошибка) ← E ← F(отмена D)

-git diff - показывает в консоли файлы которые были изменены но не были добавлены в git add 
-git diff --staged - показывает что готово к коммиту и на сколько я понял что находится в git add 
-git diff HEAD - сравнивает рабочую папку и последний коммит и показывает что изменилось 
-git diff ветка1 ветка2 - сравнивает две ветки и показывает все файлы которые отличаются между ними. 

- git clone url - скачивает полностью репозиторий указанный по ссылке и настраивает его к работе. 
-git clone url папка - скачивает определеную папку.
- git clone --depth 1 url - полностью скачивает последний коммит
- git clone --branch url - скачивает полностью ветку 

Стратегия ветвления - это правила, по которым ведётся разработка в Git, там определяется, какие ветки всегда будут жить, как называть переменные, а также как и когда можно делать слияние веток
